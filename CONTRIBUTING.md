# Contributing to 3DGS Render

Thanks for your interest in improving 3DGS Render. This project moved to community-led maintenance in 2026 and is still shaking out its processes — this document exists to save you from rediscovering things the hard way, and to save the maintainers from asking every contributor the same questions.

If anything here is out of date or unclear, please open a PR against this file. That's the best possible first contribution.

## Before you start

**Supported Blender versions.** 5.2 and newer is the primary target. The addon still installs on 5.1.x and is expected to work, but that path is best-effort — maintainers do not actively test on 5.1 before merging.

**Feature status.** The [README](README.md) marks some features as *Experimental* (proxy rigs, bake pipeline, realtime relighting, mesh-to-splat conversion). Behavior can vary across GPUs and scenes; report bugs on experimental features but don't expect them to be treated as release-blocking.

**Ask questions before opening an issue.** Use [GitHub Discussions](https://github.com/Kiri-Innovation/3dgs-render-blender-addon/discussions) for "how do I …?", "is this a bug?", or "does anyone else see …?" — the issue tracker is for confirmed bugs and concrete feature requests.

## Development setup

### 1. Fork and clone

```bash
git clone https://github.com/<your-user>/3dgs-render-blender-addon.git
cd 3dgs-render-blender-addon
git remote add upstream https://github.com/Kiri-Innovation/3dgs-render-blender-addon.git
```

### 2. Get the wheels

The addon depends on packaged Python wheels (`open3d`, `scipy`, `markupsafe`, plus platform-independent ones). **The `wheels/` directory is not tracked in git** — it's only distributed inside the release zips. You need it to enable the addon.

- Go to the [Releases page](https://github.com/Kiri-Innovation/3dgs-render-blender-addon/releases).
- Download the latest release zip that matches your Blender version and OS.
- Extract just the `wheels/` directory from the zip into the root of your working copy.

Your tree should end up looking like:

```
3dgs-render-blender-addon/
├── __init__.py
├── blender_manifest.toml
├── src/
├── assets/
└── wheels/          ← from the release zip
    ├── any/
    ├── linux/
    ├── macos/
    └── windows/
```

### 3. Symlink into Blender's extensions directory

This lets you edit files in your working copy and have Blender pick up the changes on next reload.

- **macOS**
  ```bash
  ln -s "$PWD" "$HOME/Library/Application Support/Blender/<version>/extensions/user_default/dgs_render_by_kiri_engine"
  ```
- **Linux**
  ```bash
  ln -s "$PWD" "$HOME/.config/blender/<version>/extensions/user_default/dgs_render_by_kiri_engine"
  ```
- **Windows (PowerShell, run as Administrator once)**
  ```powershell
  New-Item -ItemType SymbolicLink -Path "$env:APPDATA\Blender Foundation\Blender\<version>\extensions\user_default\dgs_render_by_kiri_engine" -Target "$PWD"
  ```

Replace `<version>` with your Blender version (e.g. `5.2`).

### 4. Enable the extension in Blender

1. Launch Blender **from a terminal**, so Python errors are visible in your shell rather than only in Blender's system console.
2. Open `Edit → Preferences → Get Extensions`.
3. Click the refresh icon (⟳) so Blender rescans user extensions.
4. Under *Installed*, find **3DGS Render by KIRI Engine** and tick the checkbox.

**DO NOT click "Uninstall" from the Extensions panel while your dev tree is symlinked in.** Blender treats uninstall as `rm -rf` on the extension directory and will delete your working copy through the symlink.

After Python-side changes, disable then re-enable the extension (or restart Blender) — Blender caches imported modules.

## Making a change

1. Create a branch off the current default branch: `git switch -c <type>/<short-description>` where `<type>` is one of `fix`, `feat`, `docs`, `refactor`, `chore`. Example: `fix/animate-modifier-socket-26`.
2. Make focused changes — one PR per logical change. Drive-by refactors belong in their own PR.
3. Test manually in Blender (see [Testing](#testing)).
4. Commit with clear messages (see [Commit messages](#commit-messages)).
5. Push and open a PR (see [Submitting your PR](#submitting-your-pr)).

## Code style

The addon was originally generated by [Serpens](https://blendermarket.com/products/serpens) — you'll notice identifiers like `SNA_OT_*_<HEX>`, `Socket_50`, `attr_XXXXX`, and function names ending in hex. Some of the style rules below only make sense in that context. We are migrating out of this convention and the serpens generated code but until then we will work with this convention. This section will be updated once such a migration is complete

### General

- **Prefer editing files in `src/` over the top-level `__init__.py`.** The 2026 refactor split the addon into modules; adding new code back to `__init__.py` reverses that.
- **Preserve KIRI-prefixed names.** Geometry-node groups (`KIRI_3DGS_Render_GN`, etc.), the render material (`KIRI_3DGS_Render_Material`), and object properties (`sna_dgs_object_properties`) are load-bearing — renaming them will break every `.blend` file that already imported splats with this addon.
- **Preserve `bpy.context.view_layer.objects.active` chains** in SNA-generated code. They look verbose but the generator emits them for a reason (context awareness across UI panels vs operators).
- **No emojis in code, commit messages, or PR bodies** unless the user (contributor or maintainer) is being intentional about them.
- **Import order** in new files should follow the pattern used in existing files under `src/`:
  ```python
  import os as _kiri_os
  __file__ = _kiri_os.path.join(_kiri_os.path.dirname(_kiri_os.path.dirname(__file__)), '__init__.py')
  del _kiri_os

  from .important import *
  # then any per-module imports

  __package__ = __package__.rsplit('.', 1)[0]
  ```

### Comments

- Default to **no comments**. Well-named identifiers already explain WHAT the code does.
- Add a comment only when the WHY is non-obvious: a hidden constraint, a workaround for a specific bug, behavior that would surprise a reader.
- Don't reference PR numbers, issue numbers, or commit hashes in comments — that context belongs in the git history and rots as the codebase evolves.

### Geometry Nodes socket access

Since PR #65, `src/important.py` installs a compatibility shim (`install_geometry_nodes_52_compat`) that makes `modifier['Socket_N']` and `modifier['Socket_N'] = value` work transparently across Blender 5.1 and 5.2+.

- **For read/write in Python code:** just use `modifier['Socket_N']` / `modifier['Socket_N'] = value` — the shim handles the routing. Don't reintroduce the raw `.inputs.<sock>.value` path; wrapping it in the shim keeps every call site consistent.
- **For UI code (`layout.prop`, `layout.prop_search`)**, use `kiri_geometry_nodes_ui_target` — see the examples in the various `src/*_function_interface.py` files:
  ```python
  layout.prop(*kiri_geometry_nodes_ui_target(mod, '["Socket_50"]'), text='Update Mode')
  ```

### Wheels and dependencies

- **Don't add new runtime dependencies casually.** Every dependency ships as a per-platform wheel and inflates every release. If you must add one, add wheels for `any/`, `linux/`, `macos/`, `windows/` and update `blender_manifest.toml`.
- The `wheels/` directory stays out of git. Only maintainers touch it, and only when building releases.

### Node group edits

- The source of truth for geometry-node groups is `assets/3DGS Render APPEND V5.blend`. Edits happen in the node editor inside Blender, then the file is saved and committed.
- **Socket identifiers** (`Socket_N`) are auto-assigned by Blender when a socket is first added; they do not change if you rename or move the socket, and they are referenced by name from Python. Adding a new socket is safe; removing or renumbering an existing socket will break every call site that references it. Grep before you delete.

## Testing

There is no automated test suite. Every change must be exercised manually in Blender.

At minimum, before submitting a PR verify:

- The addon still **enables cleanly** (no errors on `Edit → Preferences → Add-ons → check`).
- The primary user flow the PR touches still works. If your PR is scoped to imports, run `Import → 3DGS Ply`. If it's scoped to export, do a `.ply` export. If it's UI-only, open every panel your change affects.
- **On Blender 5.2** at minimum. Testing on 5.1 as well is welcome but not required for merge.
- **Watch the system console** during your test (this is why launching Blender from a terminal matters). A silent no-op with a swallowed exception is a bug.

Describe what you tested in the PR body.

## Commit messages

- **One line preferred.** Aim for ~10 words, imperative mood: `wrap Animate_GN Socket_26 for 5.2 compat`, not `Fixed Bug`.
- Body is optional. Only add one if there's something the diff and PR body can't say (a subtle invariant, a linked incident, a decision that deserves a paragraph).
- No trailer requirements — this project does not require DCO sign-off or CLA acknowledgment.

## Submitting your PR

1. Push to your fork and open a PR against `main`.
2. Fill in the [PR template](.github/PULL_REQUEST_TEMPLATE.md) that appears — Summary, Testing, Screenshots, Checklist.
3. **Keep "Allow edits from maintainers" enabled** (it's on by default for PRs from forks). Maintainers may push small follow-up commits (typo fixes, one-line wraps, comment tweaks) instead of asking you to iterate, when the fix is trivial. You'll always see the change before merge.
4. **One PR per logical change.** If you find an unrelated bug while working on your fix, open a separate PR for it.
5. **PR title**: short (< 70 chars), imperative, no leading emoji or `[tag]` prefixes.
6. If your PR fixes an open issue, link it with `Fixes #123` in the body.

### What a maintainer will check

To help you self-review, this is roughly what happens on the maintainer side:

- **Does it work?** The maintainer will pull the branch and exercise the affected flow on Blender 5.2.
- **Is the diff focused?** Unrelated changes are asked to move to a separate PR.
- **Are wheel and asset paths still valid?** If the PR touches `blender_manifest.toml` or `assets/`, the maintainer confirms the release zip still assembles.
- **Is the change documented?** Look at the PR body — a reader in 12 months should understand what changed and why.

Expected turnaround for a first response: within a week. Complex PRs may take longer, and simple ones are often merged within a day or two. If a PR sits open with no activity for two weeks, feel free to ping it.

## Release process (maintainers only)

For reference, this is what happens when a release is cut:

1. Confirm `bl_info["version"]` in `__init__.py` and `version` in `blender_manifest.toml` match, and bump both if you haven't.
2. Assemble the release zip:
    - Everything currently in the repo, plus
    - The `wheels/` directory (this is the critical step — a release zip without wheels bricks the addon for users; see PR #62 aftermath).
    - Optionally, the demo `.blend` file if updated.
3. Publish a GitHub Release, upload the zip, and write release notes that call out:
    - User-visible changes.
    - Any breaking changes or known issues.
    - Which Blender versions were tested.
